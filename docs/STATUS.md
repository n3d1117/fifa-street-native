### iOS/tvOS next

Measured: iOS device lean installation, Documents data fallback, isolated user directory, automated live play, telemetry and native-log retrieval; iOS and tvOS Simulators render the language screen. Unverified: physical controller input, audible audio, saves, quiet device cadence, sustained thermals and tvOS controller/TV-safe UI.

0. **tvOS controller input (open).** A paired DualSense works in the Apple TV UI but not in the app. With `GCSupportedGameControllers` (ExtendedGamepad, MicroGamepad), a `GCEventViewController` root with `controllerUserInteractionEnabled = NO`, and a direct GameController read (`PS2X_TRACE_INPUT=1` reports `init: 0 GameController(s)` then `1 GameController(s): "Remote" "Siri Remote" extended=0 micro=1`), the app is only ever offered the Siri Remote. The same log shows `axes=0,-1,0,0` at rest for the remote path, which needs checking. Next: repeat `./rx device run --seconds 40 --env PS2X_TRACE_INPUT=1` while pressing the controller (a sleeping pad is not offered to apps) and capture `pymobiledevice3 syslog live` filtered on `GameController`, to separate "pad asleep" from a missing claim; if the pad is awake and still absent, check the app-client configuration tvOS sends to `gamecontrollerd`.

1. **tvOS gameplay pacing and audio (open).** The persistent freeze is fixed: Metal's flood guard previously recorded time before `nextDrawable`, letting each drawable-pool wait count as spacing for the next catch-up present. Recording completed acquisition breaks that feedback without changing guest clocks, VBlank delivery, priorities, semaphore signals or invocation rules. With the guard disabled, the guest freezes during the intro; enabled, the clean route sustains live play. Kill-switch: `RRV_PCSX2_GS_PRESENT_MIN_US=0`.

   The remaining NTSC 60 Hz shortfall is EE throughput in the guest's heavy scenes, not pacing, rendering or audio plumbing. `./rx device run --seconds 100 --breakdown` at 3x/8 measures present 18.46 ms mean (54.2 fps) with `cpu_game_ms` 13.42 mean and 19.58 at p90. Frames above 18 ms add guest code (`other_ms` 5.4 → 13.2), IOP 1.7 → 3.1, SPU2 0.7 → 1.2 and VIF unpack 0.8 → 1.7 ms; VU1 rises 5.8 → 11.0 ms on the worker. GPU (10.2 ms) and pipelines are flat across those frames, and register readbacks and VU1-memory barrier waits are zero, so the guest's own workload is the limit. At PAL 50 Hz the same route fits its longer field: present 20.18 ms, zero audio underruns, drain wait 0.27 ms.

   At the user's requested 1x with anisotropy off, a five-minute probe without continuous DVT collectors starts near 60 fps and slows after about two minutes; GameThread, VU and GS CPU costs rise together while GPU time stays low. Host frequency/thermal throttling is inferred, not measured by the coarse thermal-state counter. The user hears crackling during normal play and replays even though this run has zero output-ring underruns and zero runtime pipeline compiles. Next: capture producer and callback PCM to distinguish guest-source starvation from output/device artifacts, then reduce sustained CPU cost. Clock-cache TLS removal did not establish a repeatable A/B gain and was dropped. Guest clocks and NTSC mode remain unchanged.
